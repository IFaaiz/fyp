# FYP direct-label annotation guide

**Schema:** `fyp-direct-label-v1`
**Use:** independent human calibration and later human-adjudicated TRAIN data
**Policy status:** freeze these rules for Round 1; write proposed changes in the adjudication log before changing the guide.

## 1. What annotators do

Read the current authored message, decide whether it concerns project work, select the FYP labels that apply directly, and mark the exact words that support each selected label. Labels describe the message as written now. Earlier thread text can help explain a reminder, but quoted historical words do not count as evidence in the current message.

Keep classification and extraction separate:

- **Classification:** select zero or more direct FYP labels after resolving scope.
- **Extraction:** mark exact source spans and link the useful spans to each selected label.

Do not create Meeting, Task, Document, Approval, or Project Update acts for another system to convert. The human record stores the final FYP categories.

## 2. Decide project relevance first

`scope.value` is one of:

- `PROJECT`: the current message shows a bounded initiative, workstream, milestone, or project deliverable.
- `NON_PROJECT`: the current message is clearly routine business, personal, or unrelated work. Store `labels: ["NON_PROJECT"]` and no project labels.
- `UNCERTAIN`: the message does not establish whether it is project work. Set `needs_review: true`, give a short `scope.reason`, and leave `labels` empty. Do not turn uncertain scope into gold project labels.

The word “project,” a department name, a report, or a date does not establish scope by itself. Use the current authored message and the permitted context in the app. If a quoted passage is the only evidence, select `UNCERTAIN` or record a review reason.

## 3. Direct FYP labels

For `PROJECT`, select every category that applies. Do not choose a dominant category. The eight project labels are:

| Label | Apply it when the current message… | Boundary |
|---|---|---|
| `MEETING` | schedules, confirms, changes, cancels, or substantively discusses a specific project meeting, call, or workshop. | A meeting date is not a deadline. |
| `DEADLINE` | sets, changes, confirms, or follows up on a due date or time for a project action or deliverable. | A date of occurrence or meeting alone is not a due date. Mark the due phrase and what it applies to when stated. |
| `REPORT_REQUEST` | requests, expects, or follows up on preparing, submitting, or providing a formal project document or deliverable. | Delivery or mention of an existing document is not itself a request. A raw file or dataset is not automatically a formal deliverable. |
| `DEPARTMENTAL_INPUT` | requests, tracks, or reports a project contribution, input, data, feedback, or decision from a department or organizational unit. | A department mention or recipient name alone does not qualify. |
| `ACTION_REQUEST` | requests, assigns, or directs a concrete operational project task. | Use it only for a task distinct from the document transfer, departmental contribution, or approval request already represented by another selected label. |
| `FOLLOW_UP` | reminds, chases, checks, or escalates a previously expected project action, response, document, approval, or contribution. | A first request is not a follow-up. Current reminder/chase wording is required. Use available thread context to identify the prior expectation; do not invent a link. |
| `APPROVAL` | requests, grants, rejects, withholds, or conditions formal project approval, sign-off, or authorization. | Ordinary review, comments, or feedback are not approval. |
| `GENERAL_UPDATE` | communicates meaningful project progress, completion, blocker, decision, status, or change in work state. | It is not a generic fallback for any informative sentence. |

`NON_PROJECT` is generated by scope and is exclusive. It is the only label for `NON_PROJECT` scope. It cannot co-occur with a project label.

## 4. Frozen co-occurrence policy

Apply these rules consistently, including when an email contains several clauses:

- **A requested report with a due date:** “Please send the revised report by Friday” is `REPORT_REQUEST` + `DEADLINE`. Do not add `ACTION_REQUEST` for the same act of sending the report.
- **A distinct second task:** “Please test the system and send the report” is `ACTION_REQUEST` + `REPORT_REQUEST`. Add `DEADLINE` only if a due date is stated.
- **Department contribution:** “Finance, please provide the figures by Thursday” is `DEPARTMENTAL_INPUT` + `DEADLINE`. Add `REPORT_REQUEST` only when the requested item meets the project’s formal deliverable definition. Add `ACTION_REQUEST` only for another distinct operational task.
- **Approval and review:** “Please review the draft” is usually `ACTION_REQUEST`, not `APPROVAL`. “Please approve the draft” is `APPROVAL`. A communicated formal approval decision is `APPROVAL` + `GENERAL_UPDATE`.
- **Deadline change:** an explicit changed due date is `DEADLINE` + `GENERAL_UPDATE` because the message communicates a project-state change. A meeting reschedule remains `MEETING`; it does not become `DEADLINE`.
- **Completed departmental contribution:** a message saying the requested departmental input has arrived is `DEPARTMENTAL_INPUT` + `GENERAL_UPDATE`.
- **Document delivery or missing document:** “The report was sent” is `GENERAL_UPDATE`, not `REPORT_REQUEST`. “The report is still missing” is `GENERAL_UPDATE`; add `FOLLOW_UP` when the current message explicitly chases or reminds about the outstanding expectation.
- **Meeting and due date in one message:** label both separately only when the text identifies both a meeting time and a due date, for example “Meet Friday; the report is due Monday.”
- **Review completion:** a review request is not formal approval. A completed ordinary review may be `GENERAL_UPDATE`; use `ACTION_REQUEST` only when the current message assigns the review as work.

When one clause supports more than one label under these rules, link the same evidence span to each relevant label. Do not duplicate the span record.

## 5. Mark evidence and fields

For every selected project label, add one `label_support` entry. Put at least one current-message evidence span ID in `evidence_span_ids`. Put extracted dates, people, departments, requested items, or other fields in `field_span_ids`. A selected label with unclear interpretation may carry a concise `review_reason`; set `needs_review: true` and add a `review_reasons` entry for the record. `NON_PROJECT` comes from scope and does not have a project-label support row.

Use exact, minimal spans. Offsets are Unicode code-point character offsets into the unchanged `subject` or current authored message, with half-open ranges `[start, end)`. The selected text must equal the corresponding source field’s `[start:end]` slice. Do not anchor evidence to a quoted older request, a signature, or email metadata.

Use `EVIDENCE` for the phrase that supports the scope decision or a selected label. Use these supported `type` values for specific evidence and extracted fields:

- `EVIDENCE`, `PROJECT`
- `MEETING_DATE`, `MEETING_TIME`, `PARTICIPANT`, `AGENDA`
- `DEADLINE_DATE`, `DEADLINE_TIME`
- `REQUESTED_DOCUMENT`, `DEPARTMENT`
- `ACTION_ITEM`, `RESPONSIBLE_PARTY`
- `INPUT`, `APPROVAL_TARGET`

Use a label-specific trigger or status span as evidence, then add the date, person, department, or deliverable span as a field where it helps. Do not mark every sentence. If a selected category has no support in the current message, revisit the label or mark the record for review.

For a deadline, mark the due-date/time phrase and identify what it applies to when the message says so. For a follow-up, mark current reminder wording. Set `follow_up_target` to the best available value: `TASK`, `DOCUMENT_REQUEST`, `APPROVAL`, `DEPARTMENT_INPUT`, `MEETING_ACTION`, or `UNCLEAR`. Use `UNCLEAR` and `needs_review` when the expectation cannot be identified. A graph link is not required in this round.

`applies_to` is a concise description of the task or deliverable the selected label concerns. Keep it grounded in the message. These fields record simple support relationships; they do not replace direct label selection.

## 6. Record shape and version boundary

Every new direct record uses `schema_version: "fyp-direct-label-v1"` and includes:

- `record_id` and `current_source_id`, both equal to the immutable source ID;
- `scope: {"value": ..., "reason": ..., "evidence_span_ids": [...]}`;
- `labels`: direct FYP label strings;
- `spans`: `{id, field, start, end, text, type}` records;
- `label_support`: `{label, evidence_span_ids, field_span_ids, applies_to, follow_up_target, review_reason}` records;
- `needs_review` and `review_reasons`;
- `provenance`: the existing provenance object, server-stamped by the app.

The app supplies source text while annotating and binds the export to its immutable source hash. Spans may target `subject` or `current_message`; offsets are Unicode code-point offsets into those exact fields. Do not hand-edit server-stamped provenance. Keep old Structured V1 event records and drafts under their original schema/version; do not reinterpret or auto-map them into direct labels. A direct record is not automatically human gold. Gold status requires a separate human adjudication record with a named reviewer, time, decision, and validated source evidence.

## 7. Blind calibration and uncertainty

For blind work, do not view AI suggestions or another annotator’s answers before your own submission is frozen. Label the message from the source and this guide. If only one category is unclear, record that uncertainty and `needs_review`; do not clear the review flag just to produce an agreement score.

The comparison tool excludes an entire record pair from label, span, and support-relation agreement when either record is `UNCERTAIN`, has `needs_review`, or carries a review reason. It still counts the selected scope values in scope agreement and reports excluded review pairs separately. Exact and overlap span scores are descriptive agreement measures, not accuracy. Relations are counted separately from the direct labels.

All first-round shared examples remain in calibration. Once adjudicated, they may be used as human TRAIN examples if their provenance and eligibility pass review. They are never promoted automatically to independent validation or holdout.
